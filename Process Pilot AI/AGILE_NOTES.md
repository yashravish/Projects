## Product Backlog

|---|---|---|---|
| US-001 | As an employee, I can submit an operational request through a web form so that my request is formally tracked | Must Have | 5 |

| US-003 | As a manager, I can view all requests assigned to my team so that I can manage my queue effectively | Must Have | 5 |

## MVP Scope (Sprints 1–3)

### Included in MVP

- User authentication with JWT (employee and manager roles)
- Request submission with structured form (title, description, category, urgency)
- Automatic routing engine with keyword-based classification
- Priority scoring algorithm
- Employee dashboard showing own requests with status
- Manager queue with team requests, filtering, and status updates
- AI summary generation with mock fallback
- Analytics dashboard with overview metrics and trend charts
- Seed data with 5 demo users and sample requests
- Docker Compose for one-command local deployment
- Comprehensive documentation (README, architecture, business case)

### Deferred to Future Sprints

- Email and Slack notifications on status changes
- SLA tracking with escalation rules
- Multi-level approval workflows
- SSO/LDAP integration for enterprise authentication
- Comprehensive audit logging with export capability
- Mobile-responsive redesign with PWA support
- Performance optimization (query caching, connection pooling, pagination)
- CI/CD pipeline with automated testing
- Production Terraform deployment

## Risks and Assumptions

### Risks

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| OpenAI API rate limits or outages affect AI features | Medium | Low | Mock fallback provider ensures core functionality is unaffected |
| Database schema changes required after initial deployment | High | Medium | Alembic migrations provide controlled schema evolution |
| Scope creep from additional feature requests | High | High | Strict MVP scope defined; deferred features documented in backlog |
| Security vulnerabilities in authentication | Low | High | JWT best practices, bcrypt hashing, CORS config, input validation |
| Performance degradation with high request volume | Low | Medium | PostgreSQL indexing, pagination, and caching strategy planned for Sprint 6 |
| Team member unavailability during sprint | Medium | Medium | Cross-training on frontend and backend; documented architecture reduces bus factor |
| Cloud deployment costs exceed budget | Low | Low | Terraform scaffold uses smallest instance types; cost estimation documented |

### Assumptions

- The development team consists of 1–2 full-stack developers
- PostgreSQL is available as a local install or via Docker
- Node.js 18+ and Python 3.11+ are available in the development environment
- The OpenAI API key is optional; the application must function without it
- Demo data is sufficient for portfolio presentation; production data migration is out of scope
- The application targets modern browsers (Chrome, Firefox, Safari, Edge — latest 2 versions)

## Definition of Done

A user story is considered **Done** when all of the following are true:

- [ ] Code is written and follows project conventions (TypeScript strict mode, Python type hints)
- [ ] Unit tests cover the new functionality with >80% coverage on business logic
- [ ] API endpoints have integration tests with test database fixtures
- [ ] Code passes linting (ESLint for frontend, Ruff for backend) with zero errors
- [ ] The feature works correctly in the Docker Compose environment
- [ ] API changes are reflected in the auto-generated Swagger documentation
- [ ] The feature is accessible and functions in the latest versions of Chrome, Firefox, and Safari
- [ ] Edge cases and error states are handled with user-friendly messages
- [ ] No regressions in existing functionality (all prior tests pass)
- [ ] Code is reviewed by at least one team member (or self-reviewed with a fresh perspective for solo projects)

## Velocity and Estimation Notes

### Estimation Approach

Story points use a Fibonacci-like scale (1, 2, 3, 5, 8, 13) where:
- **1 point:** Trivial change, well-understood, <1 hour of work
- **2 points:** Small task, minor complexity, ~half day
- **3 points:** Medium task, some unknowns, ~1 day
- **5 points:** Significant task, multiple components affected, ~2 days
- **8 points:** Large task, cross-cutting concerns, ~3–4 days
- **13 points:** Epic-sized, should be broken down further

### Estimated Velocity

For a 1–2 person team working in 2-week sprints:
- **Sprint 1 (foundation):** ~30 points — higher velocity because infrastructure tasks are well-understood
- **Sprint 2 (intelligence):** ~25 points — routing and AI integration involve more design decisions
- **Sprint 3 (polish):** ~25 points — analytics, testing, and documentation require attention to detail

**Average velocity:** ~25–30 points per sprint

### Retrospective Questions

At the end of each sprint, the team would discuss:
1. What went well that we should keep doing?
2. What didn't go well that we should change?
3. What experiments should we try next sprint?
4. Were our estimates accurate? How should we calibrate?
5. Are there blockers we need to escalate?

These notes reflect agile practices as they would be applied in a real consulting engagement, adapted for the scale of a portfolio demonstration project.
